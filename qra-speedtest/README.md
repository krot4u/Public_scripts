# Проверка канала Pi-Star → QRA-XLX

Кнопка в боковой панели открывает виджет внутри дашборда. Браузер передаёт
команду PHP API под `/admin/qra-speedtest/`. PHP обращается к локальному
Unix-сокету агента. Агент запускает iperf3 на самом Pi-Star, поэтому измеряется
канал устройства, а не компьютера с браузером. IP/порт задаёт администратор
при установке; пользователь виджета не может выбрать другую цель.

Тест последовательно выполняет передачу и приём для трёх профилей:

| Профиль | Продолжительность направления | Предлагаемая нагрузка | Результаты |
| --- | --- | --- | --- |
| TCP | 5 с | до 10 Мбит/с | Скорость приёмника |
| UDP | 5 с | 1 Мбит/с, 1200 байт | Скорость, потери, джиттер приёмника |
| DMR | 12 с | 7333 бит/с, 55 байт, примерно 60 мс | Скорость, потери, джиттер приёмника |

Это проверка работы канала при указанной нагрузке, а не поиск максимальной
пропускной способности. Профиль DMR имитирует размер и среднюю частоту UDP
Homebrew для одного голосового потока. iperf3 использует свой формат данных
и pacing ОС: это не настоящие DMRD-пакеты, не проверка AMBE, радиотракта,
авторизации XLX или прохождения пакетов через боевой порт 62030. Проверочный
порт должен быть отдельным. Джиттер — статистика iperf3, не задержка в одну
сторону; RTT/ping здесь не измеряется. Между устройствами не нужна синхронизация
часов. Нагрузочный тест может ухудшить текущую голосовую связь, запускайте в паузе.

Образец формата пакета: [MMDVM DMRNetwork.cpp](https://github.com/g4klx/MMDVM-Host/blob/master/DMRNetwork.cpp),
длительность слота: [DMRDefines.h](https://github.com/g4klx/MMDVM-Host/blob/master/DMRDefines.h).
Параметры теста: [документация iperf3](https://software.es.net/iperf/invoking.html).

## Установка при согласованном развёртывании

Требуются Linux/systemd, Python ≥3.7, PHP ≥7, iperf3, веб-группа `www-data`.
Серверная версия iperf3 должна поддерживать `--server-max-duration`,
`--server-bitrate-limit` и `--idle-timeout`; установщик проверяет это до изменения
сервиса. Локальный сетевой прогон выполнен на iperf3 3.22. Проверенный 19.11.2026
пакет 3.9 на QRA-XLX этих ограничений не поддерживает. В прототипе iperf3 3.22
собран отдельно в `/opt/qra-speedtest/iperf`, штатный пакет сохранён.

1. На сервере выделите IPv4 и отдельный непривилегированный порт. По прямому
   требованию пользователя TCP **и** UDP этого порта доступны всем IPv4-клиентам,
   без ограничения по адресу источника и без отдельной аутентификации iperf3.
   Сервер обслуживает одну проверку одновременно; остальные
   устройства получат ошибку занятости. Лимит сервера — 25 Мбит/с, 15 с на тест.
2. На QRA-XLX из каталога модуля выполните от root
   `bash install-server.sh BIND_IPV4 PORT`, подставив проверенные адрес и порт.
   Сервис: `qra-speedtest-server.service`. Боевой xlxd не меняется.
   Для отдельного бинарника задайте `IPERF_BIN=/opt/qra-speedtest/iperf/bin/iperf3`
   перед командой установщика. `deploy/open-server-port.sh` открывает только
   выбранный порт через собственную цепочку QRA_SPEEDTEST перед каждым запуском
   сервиса и удаляет только собственные переходы для прежних портов.
3. На Pi-Star установите зависимости штатным способом для его образа,
   переведите файловую систему в RW и скопируйте полный каталог модуля.
   Выполните от root `bash install-client.sh SERVER_HOST PORT`. Сервис:
   `qra-speedtest.service`, конфигурация: `/etc/qra-speedtest.json`.
   Неподдерживаемый Python или отсутствие iperf3 останавливают установку.
   Имя сервера разрешается и сохраняется как IPv4. `deploy/allow-client-port.py`
   добавляет только исходящие TCP/UDP-разрешения к этому адресу/порту, удаляя
   свои устаревшие правила при перенастройке. Installer и updater подключают
   общий guarded hook в `/root/ipv4.fw`; существующий файл предварительно
   сохраняется как `/root/ipv4.fw.qra-speedtest-backup`.
4. Установите подготовленные файлы дашборда из Public_scripts. Проверьте,
   что веб-сервер защищает весь `/admin/`, включая вложенный API,
   существующей авторизацией Pi-Star; API намеренно не создаёт отдельный логин.
   Откройте дашборд, кнопку проверки и запустите тест в паузе голосового обмена.
   Ожидаемый результат — шесть строк с направлениями от лица Pi-Star.

Оба установщика применяют `deploy/disable-ipv6.sh` и сохраняют отключение IPv6
в `/etc/sysctl.d/90-qra-speedtest-ipv4.conf`. Это выполняется при первой
установке, включая штатный обновлятор. Отдельные установщики требуют готовый
iperf3; штатный обновлятор устанавливает недостающий пакет через apt без обновления ОС. Изменения firewall ограничены
выделенным портом сервера и исходящим endpoint клиента.

## Цветовая оценка

Основной экран показывает один результат и короткое пояснение. Во время
проверки индикатор движется; после завершения он остаётся неподвижным.
Технические метрики, стадии и параметры нагрузки находятся в закрытых
«Подробностях». При `prefers-reduced-motion` движение отключается.

Практические пороги прототипа применяются к худшему направлению синтетического
DMR-потока. Это продуктовая эвристика, а не норматив протокола DMR:

| Цвет | Результат | Условие |
| --- | --- | --- |
| Зелёный | Связь хорошая | Потери <1% и джиттер <20 мс |
| Жёлтый | Связь нестабильная | Потери от 1% до <3% или джиттер от 20 до <50 мс |
| Красный | Проблемы со связью | Потери ≥3% или джиттер ≥50 мс; также измеренная нулевая скорость |

Худшее условие определяет цвет. Положительная оценка требует полного набора
шести результатов и корректных метрик обоих направлений DMR. При недостатке
данных оценка нейтральная. Ошибка выполнения отдельно обозначается красным
«Проверка не завершена»: это не утверждение о неисправности сети.
Временная потеря доступа к API не сохраняет прежний зелёный статус; виджет
повторяет подключение. Логика порогов находится только в `web/quality.js`.

## Источники обновления

Исходник агента, установщики и web-файлы находятся в `qra-team/PiStar/speedtest`.
В Public_scripts публикуются согласованные копии:

- `dashboard/admin/qra-speedtest/`: widget.html, widget.css, widget.js, api.php;
- `dashboard/qra-speedtest-button.php`: include кнопки;
- `qra-speedtest/`: агент, service units, установщики, web и deploy scripts.

`PiStar/HostFilesUpdate.sh` загружает web-файлы из корня Public_scripts для
обеих версий дашборда. Четыре index.php (обычный/административный, legacy/4.3)
подключают кнопку через защищённый `is_file` include: неполная загрузка модуля
не ломает главную страницу. Агент устанавливается и проверяется при каждом штатном обновлении, даже если
версия дашборда уже актуальна. При первой установке обновлятор получает
`client-defaults.json` (QRA-XLX, IPv4, порт 55219), устанавливает недостающий
iperf3, пользователя, firewall hook и службу с автозапуском. Существующий
`/etc/qra-speedtest.json` сохраняется. Неизменный работающий агент не перезапускается;
остановленная служба запускается. Сбой загрузки или установки пакета не заменяет
установленный агент; следующая попытка выполняется при следующем обновлении.

Для выпуска нужно согласованно опубликовать Public_scripts **и** обновлённый
HostFilesUpdate в действующих S3-артефактах `HostFilesUpdate-rpi` и
`HostFilesUpdate-nano`. Изменения локальных исходников сами по себе устройства
не обновляют. Старые updater не скачивают новые зависимости. Новый updater проверяет Python
≥3.7 и группу www-data; несовместимость явно записывается в журнал. Системный
Python не заменяется. Все файлы сначала загружаются во временный каталог.

## Работающий прототип, 19.11.2026

На `http://192.168.112.25/` (Pi-Star 4.3.8, Raspberry Pi 3 Model B, Python 3.11.2,
iperf3 3.12) установлены агент и кнопка. В боковой панели выберите
«Проверить связь с QRA-XLX», затем «Запустить проверку». На QRA-XLX работает
отдельный iperf3 3.22 на TCP/UDP 55219, доступный всем IPv4-клиентам.
После явного согласия пользователя выполнен настоящий полный запуск из браузера:

| Профиль | Передача Pi-Star | Приём Pi-Star | Потери | Джиттер передачи / приёма |
| --- | --- | --- | --- | --- |
| TCP | 10,04 Мбит/с | 10,07 Мбит/с | — | — |
| UDP | 1,00 Мбит/с | 1,00 Мбит/с | 0% / 0% | 0,20 / 0,15 мс |
| DMR | 7,33 кбит/с | 7,37 кбит/с | 0% / 0% | 0,38 / 0,31 мс |

Это результаты одного прогона под заданной нагрузкой, не предельная скорость
канала и не приёмка голосового DMR-тракта. Пройдены проверки API: 401 без
авторизации, 403 с неверным CSRF, 409 при повторном запуске активного теста.
Доступ к серверному порту подтверждён со второго внешнего хоста после снятия
временного ограничения по IP. Повторное применение клиентского helper не
добавляет дубликаты: два OUTPUT-правила и один hook. XLX остался активен.

Резервные копии двух изменённых страниц устройства находятся в
`/var/backups/qra-speedtest-prototype/`. Проверяйте системные статусы
`qra-speedtest.service` на Pi-Star и `qra-speedtest-server.service` на QRA-XLX.
Прототип установлен адресно; массовый выпуск в GitHub/S3 ещё не выполнялся.

## Проверки и границы приёмки

- `python3 -m unittest discover -s PiStar/speedtest/tests -v` — выбор статистики
  приёмника, параметры DMR, шесть этапов, запрет параллельного запуска и сохранение
  частичных результатов при таймауте; повторное обновление без рестарта и
  сохранение установленной версии при недокачанном пакете; миграция firewall
  на новый endpoint/порт и восстановление hook при обновлении (10 тестов).
- `node --check PiStar/speedtest/web/widget.js` и PHP lint — синтаксис.
- `node --test PiStar/speedtest/tests/quality.cjs` — 8 проверок цветов,
  граничных значений, худшего направления, неполных данных и ошибок.
- Локальный iperf3: шесть этапов, оба направления, ненулевая скорость,
  потери и джиттер UDP. Это не замер до production.
- UI test plan: открыть кнопку, проверить dialog и фокус/закрытие; повторить
  на 360 px; проверить idle → running → done, сохранение частичных результатов
  при error, повторный запуск, восстановление после сетевого сбоя и перезагрузки;
  проверить доступное имя, live-статус и явные ограничения нагрузки.
- Для воспроизводимого UI-прогона запустите из корня qra-team
  `python3 PiStar/speedtest/tests/preview.py`, затем в другом терминале
  `node PiStar/speedtest/tests/widget.cjs` с доступным модулем Playwright и Chrome.
  Если Playwright установлен отдельно, задайте `PLAYWRIGHT_MODULE` путём к его
  модулю. Preview работает на `http://127.0.0.1:8877/` и явно помечен как fixture:
  он не проверяет PHP/авторизацию и не показывает реальные сетевые замеры.
- При установке на настоящем Pi-Star проверить Unix-сокет/права, авторизацию
  `/admin/`, прохождение TCP/UDP до QRA-XLX и повторное обновление дашборда.
  Эти проверки на устройстве не заменяются локальными тестами.
